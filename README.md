# Behavioral Detection Pipeline for Windows Host Telemetry

[![CI](https://github.com/cOmrade3267/detection-project/actions/workflows/ci.yml/badge.svg)](https://github.com/cOmrade3267/detection-project/actions/workflows/ci.yml)

Ingest Windows Sysmon/Security event logs, build per-process behavioral
features, detect attacker behavior with (a) hand-written Sigma-style rules and
(b) an unsupervised anomaly model, map alerts to MITRE ATT&CK, and evaluate
against Chainsaw/Hayabusa as a rules-only baseline — reporting precision,
recall, and false-positive volume.

> Design brief and working rules: [`CLAUDE.md`](CLAUDE.md). Design decisions:
> [`docs/design.md`](docs/design.md). Which Sigma features the rule engine
> supports: [`docs/sigma-support.md`](docs/sigma-support.md). From a real
> vulnerability to detections:
> [`docs/from-vulnerability-to-detection.md`](docs/from-vulnerability-to-detection.md).

## Research questions

1. How much attack behavior does a pure rules approach (Sigma via
   Chainsaw/Hayabusa) miss, per ATT&CK technique?
2. Does a behavioral anomaly model catch some of the misses, and at what
   false-positive cost?
3. Does combining both (rules OR model) beat either alone at a fixed alert
   budget?

## Pipeline

```
raw .evtx -> ingest -> normalize -> features -> (rules | model)
          -> alerts + ATT&CK mapping -> evaluate (vs. Chainsaw/Hayabusa)
```

## Reproduce

```bash
make setup      # create venv, install package with dev extras
make test       # run the test suite (incl. the no-leakage split check)
make smoke      # run the pipeline on the committed sample .evtx (no data needed)
```

Once you have lab data, the whole pipeline raw `.evtx` → results is one command:

```bash
make all EVTX=data/lab/raw/sample.evtx LABELS=data/lab/labels.csv   # -> artifacts/
```

Or run it per stage (each writes a Parquet the next one reads):

```bash
make ingest    EVTX=data/lab/raw/sample.evtx  OUT=data/lab/raw/sample.parquet
make normalize IN=data/lab/raw/sample.parquet OUT=data/lab/normalized/sample.parquet
# attach labels from the run log (time-window rule, docs/lab-setup.md s5):
make label     IN=data/lab/normalized/sample.parquet LABELS=data/lab/labels.csv \
               OUT=data/lab/normalized/labeled.parquet SRC=lab
# evaluate rules + model and regenerate every table and the figure:
make evaluate  EVENTS=data/lab/normalized/labeled.parquet   # -> artifacts/
# optionally fold in the external SigmaHQ baseline (Chainsaw/Hayabusa output):
make evaluate  EVENTS=data/lab/normalized/labeled.parquet EXTERNAL=hunt.json ETOOL=chainsaw
```

`make evaluate` writes `artifacts/summary.csv`, `results.md`,
`per_technique_recall.csv`/`.png`, `confidence_intervals.csv` (bootstrap 95% CIs
over sessions), `ablation.csv` (drop-one-feature-group), and
`alert_explanations.csv` (top contributing features + matching rule per alert),
and rewrites the **Results** table above from `summary.csv`. It stays `TODO`
until run on real data (no number is hand-written). For the cross-distribution
robustness check, add `--holdout lab_vs_public` (trains on lab, tests on public;
does not touch the README). `make help` lists every target.

Dependency versions are floored in `pyproject.toml` and the exact installed set
is frozen in `requirements.lock` (`make lock`) for byte-for-byte reproducible
runs — install those pinned versions with `pip install -r requirements.lock`.

Data is **not** committed. See [`data/README.md`](data/README.md) to obtain the
lab and public datasets.

## Limitations

Honest scope — these hold regardless of the (pending) measured numbers:

- **One lab host, one Sysmon config.** A single Windows AD VM is not a fleet;
  benign behavior here doesn't represent the diversity of real hosts, so
  false-positive estimates won't transfer directly.
- **Small benign set.** Precision and FP-per-10k are high-variance and likely
  optimistic on a limited benign sample; the bootstrap CIs (`make evaluate`)
  quantify that uncertainty rather than hiding it.
- **Recall is only meaningful for techniques actually run.** Coverage is limited
  to the ATT&CK techniques in `docs/lab-setup.md §4`; the per-technique table
  shows exactly which are and aren't covered.
- **Defender setting matters.** Whether Microsoft Defender was on or off changes
  which activity runs to completion and what telemetry appears; the setting used
  is recorded in `docs/lab-setup.md`.
- **Public samples are attack-only, not production traffic.** They're an
  eval-only held-out set; precision can't be measured on them (no benign).
- **Not tested at scale.** This is a single-host batch pipeline; fleet-scale
  design (streaming, per-host baselines, serving, cost) is discussed, not built,
  in [`docs/scaling.md`](docs/scaling.md).
- **Evasion.** What the design can and cannot detect, and how an attacker evades
  it (living-off-the-land, slow-and-low, poisoning), is in
  [`docs/threat-model.md`](docs/threat-model.md).
